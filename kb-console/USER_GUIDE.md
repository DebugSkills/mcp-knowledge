# 🖥️ MCP Knowledge Console — руководство пользователя

**kb-console** — веб-интерфейс для проверки и обслуживания MCP Knowledge Server: статус системы, загрузка материалов, поиск по базе знаний. Открывается в браузере на порту **8085**.

## 🚀 Запуск

**На серверном хосте** (вместе с сервером — уже настроено в compose):
```bash
docker compose up -d            # dev
# или из air-gap bundle:
./scripts/offline-deploy.sh deploy
```
→ открыть `http://localhost:8085`

**На клиентском хосте** (отдельно от сервера):
```bash
# CONSOLE_HOST=0.0.0.0 обязателен в bridge-режиме (docker-proxy ходит на IP
# контейнера, 127.0.0.1 внутри через -p недоступен); наружу публикуем loopback.
docker run -d --name kb-console \
  -e MCP_SERVER_URL=http://<server-ip>:8000 \
  -e MCP_API_KEY=<ключ из .env сервера> \
  -e CONSOLE_HOST=0.0.0.0 \
  -e CONSOLE_PASSWORD=<пароль> \
  -p 127.0.0.1:8085:8085 kb-console:prod
# без пароля: -e CONSOLE_AUTH=off  (иначе WARN в логах при каждом старте — bind 0.0.0.0)
```
→ открыть `http://localhost:8085`

## 🔐 Доступ и авторизация

Основной способ входа (035) — **страница входа `/login` + cookie-сессия**
(подписанная, HttpOnly, SameSite=Lax, **абсолютные 12ч** — не продлевается
активностью). **HTTP Basic работает параллельно** (back-compat: curl/скрипты
и браузеры с кэшированными кредами получают те же страницы и роли; WebSocket
закрыт так же, как страницы — обход невозможен):

| Переменная | Default | Назначение |
|---|---|---|
| `CONSOLE_PASSWORD` | пусто | Legacy-пароль (пустой users-стор): вход по паролю, username игнорируется. При непустом сторе игнорируется. |
| `CONSOLE_AUTH` | `auto` | `auto`: пароль/юзеры есть → auth включён; пусто + non-loopback bind → предупреждение. `off`: выключить (консоль открыта, `/login` → редирект на `/status`). `required`: ничего не задано → контейнер не стартует (прод). |
| `CONSOLE_STORAGE_SECRET` | пусто | Секрет подписи cookie-сессий. Лестница: env → файл `<dir users.jsonl>/storage_secret` (0600, атомарная запись) → ephemeral + WARNING (сессии живут до рестарта). **Ротация/удаление секрета = logout-all** (все cookie становятся невалидными). |
| `CONSOLE_TRUST_XFF` | `1` | Rate-limit логина по первому IP из `X-Forwarded-For`. Безопасно за TLS-фасадом (наш Caddy ставит XFF и отбрасывает входящие значения); при прямой публикации порта в сеть — поставьте `0` (иначе IP-ключ можно спуфить). |
| `CONSOLE_ADMIN_CONTACT` | пусто | Telegram-контакт админа: на `/login` появляется кнопка «Написать администратору» (t.me с готовым шаблоном заявки). Пусто (air-gap) — кнопки нет. |

- **Вход:** откройте консоль → редирект на `/login` → форма (логин+пароль или
  только пароль в legacy-режиме) → редирект на исходную страницу. Лимит:
  10 неудачных попыток / 5 мин / IP (HTTP 429 + `Retry-After`).
- **Выход:** кнопка **«Выйти»** в хедере (username виден рядом) → `POST /api/logout`
  (cookie обнуляется) → редирект на `/login`. Открытый websocket закрывается
  вместе с перезагрузкой страницы. Cookie — stateless signed: техническое
  «повторное использование» старого значения cookie возможно до конца его 12ч
  (сервер не хранит список сессий) — компромисс принят осознанно (P2-7/R9);
  полный запрет = ротация `CONSOLE_STORAGE_SECRET`.
- **Отзыв прав действует сразу:** деактивация учётки / смена роли / смена пароля
  / создание первого юзера рвёт текущие сессии на следующем запросе
  (ревалидация против `users.jsonl` + `store_version`).
- **Пароль без TLS:** страница входа шлёт пароль в теле same-origin POST —
  прямой доступ только по туннелю или TLS (см. ниже), как и раньше.
- ⚠️ **Сетевой доступ — только через туннель или TLS:** без TLS трафик виден
  в канале → `ssh -L 8085:127.0.0.1:8085` или TLS-фасад (Caddy/nginx).
  Прямая публикация порта в сеть без TLS запрещена. Cookie выпускается с
  `https_only=False` — осознанный компромисс двойного контура доступа
  (TLS-фасад :8443 И loopback HTTP :8085): cookie всегда подписана и HttpOnly,
  но без флага Secure, чтобы работал loopback-доступ.
- ✅ **Доступ из локальной сети (штатный способ, трасса code-2026-09-26-030):**
  сервис **`kb-console-tls`** (Caddy) поднимает `https://<CONSOLE_LAN_IP>:8443`
  с локальным CA (`tls internal`), allow-list подсети (`CONSOLE_LAN_CIDR`) и HSTS.
  Консоль при этом остаётся на `127.0.0.1:8085` — в сеть смотрит только фасад.
  - **Оператору:** открыть `https://192.168.2.3:8443` → страница входа → логин/пароль
    (учётки — per-user, см. «Роли и учётные записи»). При первом входе браузер
    предупредит о неизвестном CA — установить корневой сертификат
    (`data/caddy/data/caddy/pki/authorities/local/root.crt`) в доверенные
    или принять предупреждение один раз.
  - **Прокси:** если в браузере/системе есть HTTP-прокси (в т.ч. корпоративный),
    добавьте адрес консоли в исключения (no-proxy). Симптом без этого — **403 от
    Squid**, а не от консоли. На хосте это уже сделано (`NO_PROXY`), в офисе —
    переменная `console_lan_ip` в `ansible/inventory/group_vars/all.yml`.
  - Полный runbook (деплой, раздача CA, добавление оператора, troubleshooting):
    `docs/operations/console-lan-access.md`.

### 📝 Заявка на доступ (air-gap, 035)

Нет учётки — на странице `/login` откройте таб **«Заявка на доступ»**:
шаблон с 5 обязательными полями (**ФИО / Отдел / Телефон для связи /
Почта (email) / Перечень проводимых работ**), кнопка «Скопировать заявку»,
отправка по почте (`oksigen_07@bk.ru`, mailto с готовым текстом) или
администратору в чате (при заданном `CONSOLE_ADMIN_CONTACT`). Страница
не делает ни одного внешнего запроса (inline CSS/JS, favicon data-URI).

- 📎 **Safari:** не прикладывает сохранённые Basic-креды к websocket-upgrade →
  консоль работает через HTTP-polling (тоже за auth, дыры нет), но отклик чуть
  медленнее. В Chromium/Firefox — полный websocket-транспорт. С входом через
  форму (cookie-сессия) проблемы нет — Safari-кейс актуален только для Basic.

## 👥 Роли и учётные записи (code-2026-09-21-001)

Два режима авторизации: **legacy** (пустой users-стор — один пароль
`CONSOLE_PASSWORD`, username игнорируется, поведение выше) и **per-user**
(учётные записи в `users.jsonl`; при непустом сторе `CONSOLE_PASSWORD`
игнорируется полностью — warning в логах).

**Bootstrap-админ:** задайте `CONSOLE_ADMIN_USER` + `CONSOLE_ADMIN_PASSWORD`
(.compose env) — при первом старте создастся админ (идемпотентно: только если
нет активного админа). Дальше — управление через страницу `/users`.

**Роли** (привилегии убывают; серверный enforcement — per-role MCP-ключи
`MCP_API_KEY_ADMIN/EDITOR/CONTRIBUTOR`, пусто → общий `MCP_API_KEY`):

| Роль | Страницы/действия | MCP-ключ |
|---|---|---|
| 🔴 admin | всё: /tokens, /users, bulk-кнопки «Качества», replace-импорт, reindex/set_zone | write |
| 🟣 editor | контент + dedup-ревью (по одному), add/update/delete fragment, replace-импорт; БЕЗ /tokens, /users, bulk, reindex/set_zone | editor (🟣, mcp_e*) |
| 🟠 contributor | добавление: импорт (без replace), add_fragment; без удаления | import |

**`/users`** (admin-only): список учёток, создание (пароль генерируется и
показывается ОДИН раз), reset пароля, смена роли, деактивация (сброшенные
креды перестают работать немедленно). Защита от self-lockout: последнего
активного админа нельзя деактивировать/понизить. Все действия пишутся в
`users_audit.jsonl` (кто/что/когда), логины — тоже.

**Ротация:** пользователи управляются в UI (`/users`), не через env;
editor/import ключи минтятся админом на `/tokens`. `users.jsonl` живёт в
volume `./data/console` (переживает пересоздание контейнера, только
pbkdf2-хэши — секретов нет) и входит в `scripts/backup.sh`.

## 📑 Страницы

### 1. Статус
Проверка «всё ли работает»:
- **Карточки компонентов** — сервер, Qdrant, Embedding, Pipeline, DLQ: ✅ зелёное = ок, ❌ красное = проблема (с деталями).
- **Метрики** — очередь, ошибки, размер коллекции, аптайм.
- **Инструменты** — все 20 MCP-инструментов, доступных для вызова.
- Страница обновляется автоматически каждые 10 секунд (кнопка «Обновить» — вручную).

### 2. Импорт
Загрузка материалов в базу знаний — **только через загрузку файла** (.md / .markdown / .txt / .pdf). Ручной ввод текста убран.

**Общий порядок** (все кнопки заблокированы до загрузки файла):
1. Нажмите **«Choose File»** → выберите `.md`, `.txt` или `.pdf`.
2. Кнопки становятся активными в зависимости от типа файла (см. ниже).
3. Заполните/проверьте поля: **тип контента**, **домен**, **предмет** (обязательные), теги (опционально).

**Кнопки (слева направо):**
- **«Преобразовать»** — PDF→текст (только для PDF; для .md/.txt неактивна).
- **«Обработать»** — AI-автоклассификация: domain/subject/tags по содержимому.
- **«Добавить»** — запуск импорта в базу знаний.

**Текстовые файлы (.md / .txt):**
1. Загрузите файл → кнопки «Обработать» и «Добавить» активны.
2. Нажмите «Обработать» → AI предложит domain/subject/tags (можно изменить вручную).
3. Нажмите «Добавить» → импорт.
4. Результат — в **«📊 Отчёт об импорте»** (см. ниже).

**PDF (3 стадии: Преобразовать → Обработать → Добавить):**
1. Загрузите `.pdf` → активна только кнопка «Преобразовать» (текстовый слой или скан — скан обработает OCR).
2. Нажмите «Преобразовать» → PDF→текст, становится активной «Обработать».
3. Нажмите «Обработать» → AI-классификация, становится активной «Добавить».
4. Нажмите «Добавить» → импорт уходит в **«📦 Очередь импорта»** (1 импорт за раз, остальные — в очередь).

**«📦 Очередь импорта»** — карточки операций внутри карточки-отчёта:
- Свёрнутая — статус + прогресс (фаза, N/M секций).
- **Шеврон ▸/▾ раскрывает построчный лог** (parsing/OCR/decompose/indexing/git/done).
- Крестик убирает завершённые (для running — отменяет импорт), «Убрать все» — чистит завершённые разом.

**«📊 Отчёт об импорте»** — большая карточка-обёртка, объединяющая:
- «📦 Очередь импорта» (3 карточки: Преобразовать / Обработать / Импорт).
- После импорта — **ярко-зелёная сводка**: «✅ Импорт выполнен», коллекция, число секций, время обработки.
- При ошибке — красная карточка с описанием ошибки.

**Ограничения PDF:** >100 МБ или >2000 страниц → ошибка с пояснением; зашифрованные PDF не поддерживаются (пароли не хранятся).

### 3. Поиск
Пробная проверка поиска по корпусу:
1. Введите запрос (естественным языком), при необходимости `top_k`.
2. Нажмите **«Найти»** → таблица результатов: заголовок, score, домен, предмет.

## ⚠️ Частые проблемы

| Симптом | Причина / решение |
|---|---|
| Браузер требует логин/пароль | Включён Basic auth (`CONSOLE_PASSWORD`): введите любой username + пароль из env. |
| Консоль не стартует: `CONSOLE_AUTH=required, но CONSOLE_PASSWORD пуст` | Задан режим `required` без пароля — задайте `CONSOLE_PASSWORD` или смените режим на `auto`. |
| «Сервер недоступен» | MCP_SERVER_URL указывает не туда; сервер не запущен (`docker ps`). |
| «Ошибка авторизации» | MCP_API_KEY не задан или не входит в ключи сервера (для импорта нужен ключ с правами записи). |
| Импорт: 0 добавлено | Проверьте domain/subject — обязательные поля; разделы с ошибками перечислены в `failed_sections`. |
| Карточка PDF: «PDF защищён паролем» | Зашифрованный PDF — расшифруйте и загрузите снова; пароли не хранятся на сервере. |
| Лог в карточке пуст | Карточка была завершена давно и удалена из очереди (записи сессионные); лог доступен пока карточка в очереди. |
| Красные карточки в Статусе | Смотрите деталь в карточке; `/health` сервера отдаёт причину (например, Qdrant недоступен). |
| Красный баннер «❌ Ошибка аутентификации (401)…» | См. «Поведение при отказе ключа» ниже. |
| Красный баннер «⛔ Доступ запрещён (403)…» | Ключ валиден, но прав недостаточно (например, read-ключ на странице «Токены») — запросите ключ нужного уровня у администратора; текст 403 НЕ предлагает «ввести ключ». |

## 🔑 Поведение при отказе ключа (code-2026-09-22-007)

Что делает консоль, когда MCP_API_KEY мёртв (401), прав не хватает (403) или сервер/сеть недоступны:

- **401 (неверный ключ)** — автообновление страницы ОСТАНАВЛИВАЕТСЯ полностью:
  0 автоматических запросов к серверу, пока ключ не починят (раньше поллеры
  молотили API каждую секунду — до ~90 req/мин). Появляется красный баннер
  «❌ Ошибка аутентификации: неверный API-ключ (401)» с кнопками
  «Проверить и продолжить» и «Обновить страницу (F5)».
- **403 (нет прав)** — то же, но текст баннера «⛔ Доступ запрещён:
  недостаточно прав (403)» — причина в уровне ключа, а не в его значении.
- **«Проверить и продолжить»** = ручной liveness-пинг `GET /data-version`,
  ровно 1 запрос на нажатие. Ответ 200 → блок снят, автообновление
  возобновляется; 401/403 → баннер остаётся; «сервер недоступен» → notify.
- **Возобновление только ручное** — кнопкой или F5; авто-зондов консоль
  не делает. F5 пересоздаёт страницу и поллеры заново.
- **Транспортный сбой (сервер недоступен / таймаут / 5xx / 429)** — стоп-баннера
  НЕТ: поллер уходит в экспоненциальный бэкофф ×2 (1→2→4→8→16…до 60 с);
  после 5-го сбоя подряд частота ≤4 req/мин. Первый одиночный сбой интервал
  не растягивает. Восстановление соединения возвращает штатный интервал
  автоматически.
- **404 ≠ сбой**: «скан не запущен», «импорт не найден» — штатные ответы,
  бэкоффа и баннера нет.
- One-shot действия (создать/отозвать/rotate токен) при 401/403 показывают
  тот же баннер, при недоступности сервера — уведомление «Сервер недоступен».

## 🔧 Конфигурация (env)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MCP_SERVER_URL` | `http://localhost:8000` | Адрес MCP-сервера (на клиентском хосте — IP сервера) |

| `CONSOLE_AUTH` | `auto` | Режим auth: `auto` / `off` / `required` (см. «Доступ и авторизация») |
| `REFRESH_SECONDS` | `10` | Интервал автообновления страницы «Статус» |
